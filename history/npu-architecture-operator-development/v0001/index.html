1. 阅读路线：从会算，到安排它高效地算

算子开发的核心，不只是写出数学公式，而是安排：谁来算、数据放哪里、每次算多少、何时可以读取或复用缓冲。
学习路线｜四个问题，逐层深入
① 计算② 结构③ 数据流④ 开发
Cube / Vector

如何支撑计算？		分块、流水、同步
如何减少等待？		Host / Kernel
如何实现与验证？

前置认识：Cube 擅长密集矩阵乘累加；Vector 擅长逐元素及适合向量化的运算。本文从这个基础向 NPU 结构与算子开发延伸，与 Loss／反向传播主题分开，也不重复前篇全部矩阵乘法推导。

本页三种信息，请区别阅读

  • 通用原理：计算与数据搬运的关系、链路依赖、分块和数据复用。
  • 官方示例中已核实：Ascend 样例里的 CopyIn / Compute / CopyOut、队列、Host tiling，以及矩阵布局转换。来源列于页尾。
  • 教学假设：四个核任务、128 元素一块、64×64 矩阵块等，是用于算清过程的示意值，不是硬件参数或最优配置。

尚未指定 NPU 型号与 CANN 版本。因此本文是可离线阅读的原理与开发入门教程，不是已在目标硬件编译、测试过的工程。代码块全部标明伪代码；具体存储容量、通路、对齐、指令与 API 以目标环境为准。

图中不是“一张 NPU 只有一个 Cube 和一个 Vector”。NPU 往往具有多个执行资源。不同代际可能采用不同的 Cube／Vector 组织方式，包括组合或分离的设计；不能默认每个物理核都包含同样的单元，也不能把逻辑工作块数机械等同于物理核心数。

这些是理解算子的主要角色，而不是完整芯片部件清单。并非任意存储之间都可以直接传输；执行通路受到硬件和指令约束。

3. 为什么需要多级存储：算得快，不代表喂得饱

若每做一次乘加都从全局内存重新取两个数、再写回部分和，计算单元容易被数据搬运拖住。片上存储让输入得以复用，也让中间结果不必反复离开计算侧。

阅读昇腾资料时，常见名称怎么理解？

名称可先建立的理解不要误解为
GM设备全局地址空间中的张量存储每个核私有的一小块内存
L2某些架构中的片上缓存层级开发者总能任意分配的临时数组
UB / Unified Buffer与 Vector 数据处理相关的局部缓冲必然向所有计算核统一共享
L1、L0A / L0B常见架构中用于矩阵数据暂存与供数的层级必须与 CPU 缓存具有相同管理机制
L0C 等累加存储保存矩阵乘的部分和／结果每次乘加都要回到 GM 的普通输出数组

名称仅用于对照常见术语。不同芯片的容量、物理归属、可访问关系与输出通路不完全相同。某条具体路径能否直接走通，需要核对型号文档；本文不把所有架构画成固定的 GM → L1 → L0 → UB 链。

片上缓冲像工作台：小，但靠近计算。算子优化要决定每次放什么、用几次、什么时候换下一批。

4. 数学里的行列，不等于内存里的连续片段

前篇用“左矩阵取列、右矩阵取行”的外积视角解释复用。但这不意味着每次都从 GM 零散地读取一条列向量。

图 3｜同一个矩阵：二维数学视图与一维物理排列
二维矩阵 A[1 2 3 4]
[5 6 7 8]
假设按行连续存放1 → 2 → 3 → 4 → 5 → 6 → 7 → 8
取第二列取出 2 与 6：相邻行之间跨越 4 个元素，并不连续。

实际可能先搬入较大的连续块，再通过支持的搬运、转置或布局转换形成计算需要的块。部分格式转换可以与搬运结合，具体取决于能力与 API。

官方历史 MatMul 样例中就能看到 ND → NZ 等布局准备、后续 LoadData 与 Mmad 的组合。但样例针对特定旧版环境，不能把其中的格式与调用签名当作所有新硬件的要求。

数学切分回答“哪些数参与运算”；物理布局回答“这些数放在哪里、怎样高效取到”。两者需要配合，但不是同一个问题。

5. 第一个算子：跟着一个 Add 数据块走一遍

任务：C[i] = A[i] + B[i]。先假设输入形状一致、连续存储、无广播，并且结果写入独立输出。选 Add 是为了先看清数据流，不被复杂数学分散注意力。

图 4｜一次数据块处理：搬入 → 计算 → 搬出
① 输入在 GMA 的当前片段、B 的当前片段；结果区域 C 已分配。
↓ CopyIn将有效输入搬入本任务的局部缓冲；等待数据可供计算使用。
② 局部计算Vector 执行逐元素加法：c_local = a_local + b_local。
↓ CopyOut在结果已就绪后，把有效输出写回 GM。
③ 释放／复用相关读写完成后，缓冲槽位可交给后续块。

一个基本 Kernel 的主体因此可以拆为三个职责：CopyIn、Compute、CopyOut。这也与已查阅的官方 Add 示例的组织方式一致。

缓冲容量也能算清

教学设定：每块 128 个 FP16 元素，每元素 2 字节。如果输入 A、B 和输出 C 各有一个独立缓冲：

单套数据缓冲 = 3 × 128 × 2 = 768 字节。

若三者都各准备两份槽位，则纯数据载荷为 1536 字节。实际分配还要考虑对齐、临时空间和运行时限制；这不是任何芯片的 UB 容量声明。

6. 两级切分：先分给核任务，再分成片上小块

教学例子：总共 1000 个元素，安排 4 个逻辑核任务，每个完整任务负责 256 个元素，每次处理 128 个元素。

图 5｜任务划分与尾块：使用左闭右开区间
任务负责范围第 1 块第 2 块
0[0, 256)128 个128 个
1[256, 512)128 个128 个
2[512, 768)128 个128 个
3[768, 1000)128 个104 个有效元素

先给任务分配互不重叠的输出范围，再让每个任务在自己的范围内循环。这避免了 Add 的跨任务合并。任务数由运行时映射到实际执行资源，不表示这张芯片只有四个物理核。

与硬件 API 无关的同步伪代码

# 教学伪代码：下面的读写操作视为完成后才返回
# c 为当前任务编号，不是实际 Ascend C API
base = c * 256
end  = min(base + 256, N)

for offset in range(base, end, 128):
    valid = min(128, end - offset)
    a_local = read_valid(A, offset, valid)
    b_local = read_valid(B, offset, valid)
    c_local = vector_add(a_local, b_local, valid)
    write_valid(C, offset, c_local, valid)

数学切分允许这样写；落到真实 API，还需要满足地址、长度、步长与计算指令的约束。

尾块为什么是正确性的重点？

  • 最后一块只有 104 个有效元素，不能盲目从 GM 读取 128 个，或向输出写出 128 个。
  • 如本地计算需要补齐，可使用目标环境支持的安全搬运、填充和掩码方案；局部补齐不代表允许全局越界读写。
  • 还要避免多个任务的实际写回范围因对齐处理而重叠。
  • 128、256 在这里是教学参数，不是通用最优值；真实 Tiling 应根据输入、硬件容量与测量调整。

7. 双缓冲与同步：让搬运和计算重叠，但不能抢跑

如果一个块的输入搬运、计算、输出搬运全都串行，计算单元在搬运期间可能空闲。独立执行引擎与合理缓冲让不同块的阶段有机会重叠。

图 6｜理想三阶段流水线：四个块，三阶段等时长
阶段／时段012345
输入搬运T0T1T2T3——
计算—T0T1T2T3—
输出搬运——T0T1T2T3

若每阶段耗时 t，串行四块需要 12t；上述理想流水线需要 6t。推广到 r 块，理想值为 (r+2)t，而不是 3rt。这只是展示重叠收益，不是实测加速比。真实输入／输出可能竞争同一带宽，阶段耗时也可能不相等。

双缓冲提供的是“下一块有地方放”

图 7｜输入缓冲交替使用的逻辑示意
时段槽位 A槽位 B
准备装入 T0空闲
重叠 1计算读取 T0装入 T1
重叠 2安全释放后装入 T2计算读取 T1

输出可以有自己的槽位与生命周期。双缓冲并不自动带来重叠，仍需引擎支持、正确调度和同步依赖。

同步要保护两类依赖

  • 数据就绪：搬入完成才能计算，计算完成才能读取结果并写回。
  • 空间可复用：旧数据的读者尚未完成时，不能覆盖该槽位；输出尚未读走时，不能把槽位当作空闲。

已查阅样例里的 TPipe、TQue、EnQue / DeQue 等用于组织缓冲与依赖。它们的具体语义要查对应版本；不能把源代码中调用先后简单等同于所有异步硬件操作均已完成。

双缓冲解决“能否同时放两批数据”，同步解决“这批数据是否真的能读、这块空间是否真的能覆盖”。

9. 第二个算子：Add + ReLU，先体会少搬一次的收益

一个明确的流量账本

假设 FP16、N 个元素，每个元素 2 字节；忽略缓存命中、额外临时量与重复访问，以算子边界的张量读写估算：

方案张量读写流量
单独 Add读 A、读 B、写 S6N 字节
单独 ReLU读 S、写 C4N 字节
两者分开上面两项相加10N 字节
融合读 A、读 B、写 C6N 字节

模型中的流量减少 40%，但不等于延迟必然减少 40%；启动开销、缓存、片上资源占用和实际带宽都会影响结果。若 S 还有其他必须使用它的消费者，就不能无条件省掉它的物化。

先让这两个操作在同一块局部数据上连续执行，才会真正理解：算子优化有时主要是少搬数据，不是增加算术吞吐。

10. 第三个算子：ReduceSum，第一次遇到汇合

Add 中每个输出独立，ReduceSum 则把多个输入汇总成一个结果。以 1 到 8 求和为例：

图 10｜树形求和的数学示意，不代表固定指令实现
输入1，23，45，67，8
局部相加371115
继续汇合1026
最终结果36

当输入跨多个任务时，初学者可采用清晰的两阶段方案：

  1. 每个任务处理自己的数据，先求一个局部和，写到独立的工作区位置。
  2. 第一阶段完成后，第二个 Kernel 汇总这些局部和。

不要默认同一个 Kernel 内存在可任意使用的全设备屏障，也不要直接让多个任务用普通写操作覆盖同一个输出。原子操作、跨核协作等方案需要明确的支持与语义，不是入门时的默认捷径。

归约还引入数值顺序问题：浮点加法不严格满足结合律，树形、分块与串行累加的结果可能有细微差异。测试应依据类型、累加精度与规模设定误差标准。

# 教学伪代码：每个任务独占一个输出块
C_acc = zeros(64, 64)

for k0 in [0, 64, 128, 192]:
    A_tile = load_and_prepare(A, output_rows, k0)
    B_tile = load_and_prepare(B, k0, output_cols)
    C_acc += matrix_multiply(A_tile, B_tile)

store_result(C, output_rows, output_cols, C_acc)

第一批开始时累加器必须正确初始化；后续批次要累加而不是覆盖。等该输出块的全部 K 贡献完成后再写回，是这里采用的组织方式。

与“16 对向量，各 256 次乘加”如何衔接？

一个 64×64×64 的块乘法，可以在数学上展开为 64 对列／行向量，每对贡献 64×64 次乘加。合计 262144 次 MAC，即 524288 FLOPs。完整例子有 4 个输出块、每块 4 批 K，合计 8388608 FLOPs，与 2MNK 一致。

片上容量约束会出现在哪里？

若假设输入 FP16、累加 FP32，一个 A 块 8 KiB，一个 B 块 8 KiB，一个 C 累加块 16 KiB。这只是三份逻辑数据的载荷；真实实现可能还需多级暂存、布局转换副本和双缓冲。不能把三者相加后只与 UB 容量比较，因为它们可能位于不同的存储层级。

入门时先使用目标版本提供的矩阵乘高层能力，理解形状、布局和 Tiling；再深入底层指令。不要把从头手写峰值性能 MatMul 当作第一个算子练习。

12. 怎样判断瓶颈：算力、带宽，还是等待

定义算术强度 AI 为：浮点运算数 ÷ 选定存储边界的搬运字节数。必须说明统计边界；GM、缓存与局部缓冲的流量不能混为一谈。

例子与假设计算量简化 GM 流量AI
FP16 Add
N 个元素，各输入读一次、输出写一次		N FLOPs6N 字节1/6 FLOP/Byte
FP16 方阵乘法
输入、最终输出均 FP16，理想各读／写一次		约 2n³ FLOPs6n² 字节约 n/3 FLOP/Byte

矩阵乘的第二行是理想化流量模型，实际分块可能重复读取输入，输出类型也可能不同。它解释的是：规模与复用提高时，矩阵乘更有机会用计算而不是搬运主导时间。

粗略下界可写成：T ≥ max(计算量 / 有效计算吞吐，搬运量 / 有效带宽)。当两类工作能够充分重叠时，这个 max 模型更有参考意义；实际还可能受启动、同步、布局转换和调度影响。

观察到的现象优先检查
大量时间在搬运，计算单元空闲访问连续性、重复读写、融合机会、是否受带宽限制。
计算忙，但整体吞吐不理想块形状、支持精度、填充浪费与阵列利用率。
搬运和计算都不忙任务是否太小、控制或同步是否过重、并行度是否不足。
部分核任务早早完成，少数拖尾任务划分、尾块与负载不均。

多开任务不一定更快；双缓冲不一定更快；融合也可能增加局部资源压力。应先确认正确，再用目标平台的剖析工具验证瓶颈，避免只凭公式猜测。

13. 从能运行到可信：正确性与性能检查单

先写清算子契约

  • 支持哪些形状、数据类型与布局？是否支持广播、非连续输入和空张量？
  • 输入和输出是否允许别名或原地更新？
  • 如何处理 NaN、Inf、边界值与精度误差？
  • 哪些情况应明确拒绝，而不是默认示例能处理？

测试不只测整齐的大张量

测试组目的
小于一个块、恰好一个块、刚好多一个元素检查循环范围和尾块。
不同任务数、不能均匀切分的长度检查无遗漏、无重复写与负载划分。
随机输入、零值、正负值及契约支持的特殊值与参考实现比较数值行为。
归约和矩阵乘的不同规模验证误差随累加长度的变化。
重复运行与并发环境下的受支持用法排查生命周期、同步和偶发错误。

浮点比较常采用 |实际值−参考值| ≤ atol + rtol×|参考值|；atol、rtol 应根据数据类型、运算和参考精度选择，不能任意用一个宽松阈值掩盖错误。

再测性能

  1. 预热，区分编译／初始化与稳定执行时间。
  2. 使用正确的同步或事件计时，不能只测异步提交耗时。
  3. 分别说明测的是 Kernel 本身，还是含 Host–Device 传输的端到端时间。
  4. 记录输入形状、类型、芯片、软件版本、Tiling 与任务数，才能比较。
  5. 每次尽量改变一个因素，并保留正确性回归。

本文未在 NPU 上执行、编译或测量这些教学例子；文件校验或网页展示检查不等于算子验证。

14. 实践路线与资料边界

阶段产出完成标准
1 · Add最小三阶段 Kernel能解释每块地址、有效长度、尾块与结果写回。
2 · Add + ReLU局部数据上的融合能算清省去哪些中间读写，验证数值语义。
3 · ReduceSum局部归约与分阶段合并能解释跨任务汇合及浮点误差。
